# HPC parameter tuning (Slurm)

Tunes SPEA2 and MOACO by spreading a parameter grid over a Slurm job array, then
merging every shard into one comparable workbook.

```
spec.yaml  ──make_configs.py──►  shard_0000.yaml … shard_00NN.yaml  +  _all.yaml
                                        │
                            job array (one task per shard)
                                        │
                                 checkpoints/shard_*/
                                        │
                              collect job (afterany)
                                        │
                            tuning_<run>.xlsx   ← the only workbook to read
```

## Cluster settings

Pre-filled for UCT HPC from `scripts/run_reduced.sh`:

| | |
|---|---|
| account / partition | `compsci` / `ada` |
| allocation | `--nodes=1 --ntasks=1 --cpus-per-task=20` |
| environment | `module load python/miniconda3-py3.12`, then `$HOME/movrptw-venv` |
| run directory | `/scratch/$USER/movrptw/runs` |
| mail | `sprlaw001@myuct.ac.za`, on `END,FAIL` |

`--time` is the one value still worth checking — it's set to 4 h from the
reduced-instance runs, which is generous for a single shard, but confirm with a
pilot before committing 54 MOACO jobs to it.

**`n_jobs` cannot drift from `--cpus-per-task`.** `submit.sh` writes both from
its single `CPUS` variable. Worth knowing because `configs/reduced25_hard.yaml`
sets `n_jobs: 40` while `scripts/run_reduced.sh` requests `--cpus-per-task=20` —
that run oversubscribes its allocation two-to-one and will be slower than
requesting the cores it uses.

## Instances: `max_customers` vs `instances_reduced/`

The specs here use the bundled full instances with `max_customers: 25`, which
truncates to the first 25 customers at load time. Your `reduced25_*.yaml`
configs instead point at `data/instances_reduced/*_25.txt`, generated by
`scripts/make_reduced.py` — **a script that is not in this branch.**

Those two paths may not produce identical 25-customer problems (fleet size and
node selection can differ), and parameters tuned on one don't strictly transfer
to the other. Before the real sweep, pick one:

- port `make_reduced.py` into this branch, generate the reduced files, and
  change `instances:` in both specs to `data/instances_reduced/*_25.txt`
  (then drop `max_customers`), **or**
- confirm `max_customers: 25` is what your final runs will use.

## Picking the winner

```bash
python hpc/rank.py /scratch/$USER/movrptw/runs/spea2_hard/tuning_spea2_hard.xlsx
```

Prints a ranked table per algorithm and adds a `ranking` sheet to the workbook.
Don't sort the `summary` sheet by hand: it holds one row per
`instance × algorithm × params`, so a 36-point sweep over 56 instances is 2,016
rows and no single row answers "which settings should I use".

`rank.py` aggregates seeds, then instances, two ways:

- **`mean_rank`** — rank the settings within each instance, then average. This
  is the sort order, and it's what to report: it's insensitive to instance
  difficulty and is the basis for a Friedman test if you want significance.
- **`mean_hv`** — average HV across instances. Defensible because HV is
  normalised per instance to `[0, 1.1^m]`, but instances where everything scores
  badly still pull it around.

It flags the case where the two disagree — that means a setting wins big on a
few instances and loses narrowly on many. Also check **`coverage`**: the
fraction of runs that produced an admissible front. At 100 customers under hard
time windows this can drop below 1, and a setting with a strong `mean_hv` and
`coverage` 0.4 is not a good setting, it's a lucky one.

**Only that workbook is comparable.** Hypervolume is normalised by the pooled
ideal/nadir of everything written in a single pass, so the per-shard workbooks
under `workbooks/` are each on their own scale — they exist only because the
runner always writes one, and should be ignored. For the same reason, HV numbers
from a SPEA2 sweep and a MOACO sweep are *not* comparable with each other: run
both algorithms in one config (as `configs/hard_tw.yaml` does) when you want a
head-to-head, and use the tuning sweeps only to pick each algorithm's settings.

## Restarting and resuming

Everything is checkpointed per `(instance, algorithm, params, seed)`, so nothing
is ever recomputed:

- A shard that hits its time limit can be resubmitted as-is and continues.
- Resubmitting the whole sweep after adding grid points only runs the new
  combinations — but note that the generated shard *numbering* shifts when the
  grid changes, so use `--force` and let the checkpoints (keyed by parameters,
  not by shard index) do the deduplication.
- The collect job can be rerun at any time to rebuild the workbook from whatever
  has finished so far:

```bash
sbatch hpc/collect.sbatch /path/to/run_dir
```

## Sizing

| | parameter sets | runs per shard | total runs |
|---|---|---|---|
| `specs/spea2.yaml` | 36 | 280 (56 instances × 5 seeds) | 10,080 |
| `specs/moaco.yaml` | 54 | 280 | 15,120 |

Full 100-customer instances, all 56, so `download_instances.py --all` is a
prerequisite — `make_configs.py` refuses to generate if any file is missing.
`generations` (SPEA2) and `iterations` (MOACO) are held fixed so that a
"better" setting isn't just a bigger budget.

**This is a large sweep and MOACO is the risk.** Its ant construction calls
`candidate_customers()` at every insertion step, which evaluates a full
candidate route for every remaining customer, so per-run cost grows sharply with
instance size — roughly 20–60× going from 25 to 100 customers, on top of ~9×
more runs per shard than the earlier 6-instance version. 15,120 runs at that
cost is not obviously feasible inside a 48-hour shard limit.

Pilot before committing:

```bash
./hpc/submit.sh hpc/specs/moaco.yaml --pilot
```

One shard is 280 runs over 20 cores. If the pilot's elapsed time is comfortably
under the limit, launch. If it isn't, cut in this order:

1. **`n_runs: 5` → `3`** — 40% off, costs you seed-variance precision.
2. **Trim the grid** — MOACO's `beta: [2.0, 3.0, 5.0]` → `[2.0, 5.0]` takes 54
   shards to 36. Tune the ratio, not every point on it.
3. **Tune on a subset, validate on all 56** — keep one instance per Solomon
   class (C101, C201, R101, R201, RC101, RC201) in the spec, which is 9× cheaper
   and is the standard approach: settings that win across all six classes
   generalise, and the *final* experiment still runs the full 56. This is the
   cut worth making first if the pilot looks bad.

Footprint while running: `THROTTLE=6 × CPUS=20` = 120 cores, and the two sweeps
are 90 array tasks between them.
